# Туристический RAG-ассистент

Локальное приложение на Python 3.9: маршруты, рекомендации и туристическая
справка. Источники — существующий снимок Wikivoyage, пользовательские документы
и локальная ChromaDB. Модель Ollama: `qwen3:1.7b`.

## Запуск

В существующем окружении проекта:

```powershell
ollama list
.\.venv\Scripts\python.exe web_app.py
```

Открыть <http://127.0.0.1:8000>. Новых зависимостей и моделей для исправления
не требуется. Существующие статьи, векторы, пользователи и диалоги сохраняются.

При первом чтении статей автоматически создаётся
`data/cache/article_offsets.sqlite3` — индекс названий и байтовых смещений
размером около 1,5 МБ. Пересчёт эмбеддингов не нужен. Отпечаток пути, размера
и времени изменения JSONL защищает от использования устаревших смещений.

## Что вызывало ошибки

* `prepare_dataset.normalize_text` превращал статью в одну строку. Заголовки
  оставались обычными словами, маркеры `*` сохранялись, но часть названий
  отдельных записей в экспортированном тексте отсутствует. Поэтому переход
  к полной статье сам по себе проблему не решает.
* Чанки по 220 слов обрывали записи и объединяли сведения о разных объектах.
  Наличие названия в чанке подтверждало упоминание, но не владельца описания.
  В реальных данных подпись `Tower of London and Tower Bridge` непосредственно
  предшествует записи с описанием собора Святого Павла.
* В `structured_routes.py` одновременно действовали несколько вариантов
  извлечения названий и ранжирования. Входной вопрос не передавался в отбор
  остановок; часть контекста обрезалась. Географический этап дополнительно
  менял выбор по ручным приоритетам отдельных объектов.
* В `route_enrichment.py` несколько конкурирующих парсеров искали совпадения
  в смешанных чанках. Повторный семантический поиск не восстанавливал границы
  записей и мог привязать ссылку к упоминанию вместо подтверждающего факта.
* Реальная Qwen3 1.7B пропускала ID в пакетном JSON, иногда возвращала
  английский текст и искажала смысл при переводе. Проверки наличия кириллицы
  и допустимой длины этого не обнаруживали.
* Часть старых тестов подменяла модули через глобальный `sys.modules`, мешая
  общему запуску. HTTP-тесты не учитывали обязательную авторизацию, а тест
  маршрутизатора импортировал отсутствующий `request_router`.

## Как теперь строится маршрут

1. Из индекса читаются полная статья города и его подразделы, без загрузки
   всех чанков. Для трёх последних городов сохраняется ограниченный кэш.
2. Сначала разделяются записи `*`, затем предложения. Подпись перед маркером
   не считается заголовком следующей записи. Метаданные фотографий убираются
   до определения подлежащего.
3. Факт принимается, когда название является подлежащим, сохранён явный
   заголовок `Name. Description.`, либо внутри одной записи сохранилась
   конструкция о строительстве с совпадающим основным типом объекта.
   Простого упоминания рядом с гостиницей, станцией или другим объектом
   недостаточно. Сложное предложение обрывается перед новым именованным
   подлежащим.
4. Названия берутся из исходного текста. Районы, биографии людей, заголовки
   транспорта и алиасы отбрасываются. Значимость оценивается по упоминаниям
   и присутствию в основной статье; учитываются исторические, музейные,
   природные предпочтения и запрос первого знакомства. Это приблизительный
   сигнал значимости, а не официальный рейтинг популярности.
5. Частые явно выраженные отношения — размеры, материал, дата строительства,
   автор проекта, архитектурный стиль, состав коллекции, назначение — получают
   краткое русское представление с исходными значениями. Название объекта
   само по себе описания не создаёт. Таблиц достопримечательностей по городам
   и внешних туристических API нет.
6. Для других фрагментов остаётся один ограниченный вызов Qwen на объект,
   с проверкой языка, чисел, эры и основных типов. Повторов генерации нет,
   успешный результат кэшируется отдельно по исходному фрагменту и модели.
7. Ссылки перенумеровываются по статьям, из которых действительно взяты факты.
   Дни и названия выводит Python. Расстояния и время в пути не рассчитываются.

E5 загружается только при векторном поиске или работе с документами. Для
маршрута из статей энкодер не нужен. Справка, рекомендации и поиск по
пользовательским документам сохраняют существующий векторный поиск.

Для будущих экспортов `prepare_dataset.py` сохраняет дополнительное поле
`structured_text` с исходными переносами строк. Существующий `text`, чанкинг
и идентификаторы не меняются. Утраченные в текущем экспорте заголовки полностью
восстановить нельзя: неоднозначные записи могут быть пропущены.

## Проверка

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -X utf8 evaluate_rag.py routes --http
```

Первый набор включает 70 проверок: принадлежность фактов объекту, соседние
записи и фотографии, сложные предложения, алиасы, нехватку сведений, индекс
статей, три режима, авторизацию, историю, извлечение PDF/DOCX/TXT и HTTP API.

Вторая команда использует настоящие статьи и существующую ChromaDB. Она
сравнивает ответ с HTTP-маршрутом, проверяет регистрацию и сохранение истории
во временной SQLite, отсутствие загрузки E5 и повторной генерации.
Поиск пользовательских документов в этой интеграционной проверке подменён
пустым результатом; загрузка и изоляция документов проверяются отдельно.
Количество записей основной коллекции до и после проверки должно совпадать.

Артефакты:

* `data/evaluation/route_validation.json` — проверки, время и число вызовов;
* `data/evaluation/route_rome.txt` — два дня, Colosseum, Pantheon, Sistine
  Chapel, Trevi Fountain, National Museum of Rome, Galleria Borghese;
* `data/evaluation/route_paris.txt` — один день, Eiffel Tower, Notre Dame
  и Arc de Triomphe;
* `data/evaluation/route_london.txt` — два дня, Trafalgar Square, Tower Bridge,
  Buckingham Palace, St Paul's Cathedral, Tower of London, Marble Arch.

Для всех 15 остановок проверены русские описания, принадлежность фактов,
ссылки и отсутствие повторов. Парсер карточек JavaScript проверен на этих
ответах и на днях без достаточного количества объектов. Визуальная проверка
через Browser недоступна из-за ошибки подключения; цветовая схема не менялась.
Исправлено только сохранение карточки пустого дня.

## Производительность и границы проверки

Первое построение проверенных сценариев в новом процессе с готовым индексом
занимало примерно 7 с для Рима, 8 с для Парижа и 25 с для Лондона. Повторный
HTTP-запрос с кэшем — примерно 0,1–1,2 с. Это время формирования ответа,
без запуска Python и импорта зависимостей. Точные измерения текущего прогона
находятся в JSON-отчёте.

В итоговых трёх сценариях факты представлены непосредственно из источников:
**0 векторных поисков, 0 новых эмбеддингов и 0 вызовов LLM** для описаний.
Qwen3 сохраняется для остальных ответов и резервного описания сложных фактов.
Полный корпус из 226 479 чанков не загружается в память на запрос.

В интеграционном прогоне на Windows пик рабочего набора процесса Python
составил около **568 МБ**. Это отдельный процесс, без памяти сервера Ollama;
E5 в этих сценариях не загружался. Потребление всей системы с одновременно
активным поиском по документам отдельно не измерялось.

Имена собственные могут остаться на английском, грамматика резервного
перевода может быть несовершенной. Проверки резервного текста Qwen не являются
полной семантической проверкой любых исторических утверждений. Надёжность
на всех городах и всех формулировках не доказана; полностью утраченные записи
без однозначного владельца могут быть пропущены. Качество свободных справочных
и рекомендательных ответов отдельно заново не оценивалось.
